## 詳細設計

### 1. 概要と境界

Issue #67の重複防止・出所追跡を、既存の画像取込へ実装する。共通の取込記録／反映Serviceを用意し、後続のCSV等も同じ入口を利用できるようにする。実際のCSV読取、定期予定作成、現金まとめ記録の差分配分、分類学習、画像Job化、例外ダッシュボードはそれぞれ #69 / #71 / #76 / #68 / #70 / #77 の範囲とする。

同じ画像の再送は同じ取込記録を返す。確かな外部IDがあれば取込元・口座内で同一性を管理し、内容変更は訂正候補にする。IDのない類似は確認待ちにし、「同一」「別取引」を利用者が決める。反映済み／対応付け済み／却下済みは再処理しても新しい実績を作らない。

親Issue #65の「既存の実績を無断変更しない」「承認必須設定を維持」「設定変更で過去分を再処理しない」を守る。新しい自動反映設定は追加しない。既存の `image_import_requires_approval=false` は新規かつ重複懸念なしの候補にだけ適用し、保留・訂正・矛盾・旧候補は停止する。分類の確かさや不明日付の仕様改善自体は #68 で行う。

### 2. 調査基点と現状

- 確認基点: 2026-10-19に取得した `origin/main=833c3f43d36e4426edfb1568ff0e13971056fa2a`。作業ツリーの追跡ファイルも同じ内容。実装開始時には改めて最新mainを取得する（最新main起点は利用者承認済み）。
- `app/controllers/image_imports_controller.rb#create`: 画像を同期で順次解析し `items.concat` するため、抽出行と元画像の関係が失われる。画像は永続保存しない。
- `app/services/image_import_draft_builder.rb#build`: 呼出しごとにUUIDを作り、各行を個別 `create!` する。途中失敗で先行候補が残りうる。手動日付 > 抽出日付 > 当日、名称の大小文字を無視したマスタ照合。
- `ImageImportsController#apply_resolved_drafts` と `ImageImportDraftsController#bulk_approve`: 別々の取引作成ロジックで、保存後に候補を削除。二重承認・保存途中失敗の保護がない。却下も物理削除。
- `app/models/transaction.rb`: actual/plannedを持つ。予定は既に存在する。クイック入力はフォーム初期値のみ。現金まとめ記録・定期生成・日常CSV取込は未実装。
- `app/models/account_reconciliation.rb#duplicate_candidates`: 期間内の金額・カテゴリ等で事後的に候補を出す。今回の反映制御とは独立して維持する。
- 開発・標準テストはMySQL、本番はPostgreSQL。単一利用者・認証なしの現行前提を維持する。

### 3. 識別と保存データ

新規6テーブルと既存候補への参照追加を行う。各テーブルに通常のidとtimestampsを付ける。業務状態は文字列の許可リストでvalidationし、外部から状態を直接指定させない。

| モデル / テーブル | 主なカラム・制約と責務 |
|---|---|
| `ImportSource` / `import_sources` | `service_key:string(64) NOT NULL`, `account_id:bigint`, `name:string NOT NULL`, `legacy:boolean NOT NULL default false`。通常sourceはaccount必須・FKあり。`(service_key, account_id)` unique。小文字ASCII `[a-z0-9_.-]` のservice_keyを使用し、作成後service_key/accountは変更不可、表示名のみ編集可。取込がなくても削除機能は今回提供しない。legacyだけaccount=NULLを許容する固定1行。 |
| `ImportDocument` / `import_documents` | `import_source_id NOT NULL FK`, `channel:string NOT NULL`（image/legacy、将来csv等）, `content_digest:string(64) NOT NULL`, `batch_id:string NOT NULL`, `state:string NOT NULL`（received/failed/extracted）, `received_at NOT NULL`, `mime_type`, `byte_size`, `manual_date:date`, `fallback_date:date`, `pipeline_version:string`, `error_code:string`。`(import_source_id, channel, content_digest)` unique、batch_id index。原ファイルのSHA-256、初回受付日時・解析条件を保持する。 |
| `ImportIdentity` / `import_identities` | `import_source_id NOT NULL FK`, `external_id:text NOT NULL`, `external_id_digest:string(64) NOT NULL`, `bound_entry_id:bigint`（ImportEntryへ後付けFK）。`(import_source_id, external_id_digest)` unique。外部IDは数値変換・大小変換・前ゼロ除去をしない。確かなIDの一度だけの反映先を管理し、bound_entry_idは削除・解除しない。 |
| `ImportEntry` / `import_entries` | `import_document_id NOT NULL FK`, `row_number:integer NOT NULL`, `import_identity_id FK nullable`, `reference_entry_id FK nullable`（同じ外部ID・同じ内容の代表候補）, `payload:json NOT NULL`, `payload_digest:string(64) NOT NULL`, `classification:string NOT NULL`, `state:string NOT NULL`, `reason_code:string`, `target_transaction_id:bigint nullable`, `target_snapshot:json nullable`, `lock_version:integer NOT NULL default 0`。`(import_document_id,row_number)` unique、identity+payload_digest、reference_entry_id、target_transaction_idにindex。原候補・判定・反映先を保存する。target_transaction_idは削除後も残す歴史IDなのでTransactionへのFKを付けない。 |
| `ImportEvent` / `import_events` | `import_document_id NOT NULL FK`, `import_entry_id FK nullable`, `kind:string NOT NULL`, `reason_code:string`, `details:json NOT NULL`。追記専用の受付、失敗、判定、承認、対応付け、却下、矛盾検知の記録。detailsは許可項目（変更前後の候補／取引snapshot、比較先id、比較理由、選択結果、入力元種別）だけ。 |
| `ImportGuard` / `import_guards` | `name:string NOT NULL unique`。migrationで `name=ledger` を1行作成するが、その投入には依存せず、実行時にも競合安全に行を確保する（第6.3節）。すべての取込確定・判断・取引書込みの共通排他に使う。原画像も外部通信もこのロック内へ持ち込まない。 |

`image_import_drafts` に `import_entry_id`（unique、FK）を追加する。migration終了時点で全候補に割り当ててNOT NULLにする。既存の編集用カラムとbatch_idは維持し、各ImportEntryと1:1の編集用候補として残す。原文はImportEntry.payload、編集値はImageImportDraft、判断履歴はImportEventに分離する。処理後もdraftを削除せず、既定scopeでは未処理のみ表示する。後続の汎用取込Serviceも同じ編集用候補を生成でき、画像由来であることをモデル名から推定しない。

ImportSourceからAccountへは削除制限を置く（`Account#has_many :import_sources, dependent: :restrict_with_error`）。加えて `Account / Category / PaymentMethod` の各モデルへ `has_many :image_import_drafts, dependent: :restrict_with_error` を追加する。処理済み・却下済みの候補も含む関連なのでpending scopeを付けない。元口座と異なる反映口座も保護対象になる。各マスタControllerの既存のdestroy失敗時alertへ「取込候補・履歴で使用中のため削除できない」旨を出し、FK例外にしない。元のマスタ名は履歴snapshotにも残すが、今回マスタを自動的に参照解除・削除する操作は提供しない。未使用のマスタは従来どおり削除できる。

その他のsource/document/entry/eventにcascade削除を付けず、関連モデルにも削除制限を置く。取引の削除は従来どおり可能で、出所と削除前snapshotを残す。

### 4. 識別キーと原データの範囲

1. **同じ入力**: `source + channel + SHA256(元バイト列)`。ファイル名・並び順・手動日付をキーにしない。複数ファイルの同一バイト列は1文書になる。同じ画像を別名で再送しても既存の解析・結果を返す。日付指定が初回と異なる再送は解析条件を変更せず、初回指定を表示して未処理候補の編集を案内する。
2. **文書内の行**: 初回に採用した抽出配列の1始まりの位置。同一内容の2行も別候補として残す。抽出結果全行とextractedへの遷移を一括commitし、途中までの採用はしない。commit後の再送でAIを呼び直さない。
3. **確かな外部取引ID**: `source(service_key + 元口座) + SHA256(外部IDのUTF-8バイト列)`。画像AIが返す文字列は確かなIDとして使用しない。今回の画像アダプタはexternal_idを渡さない。内部Rubyの共通APIでは、将来の検証済みアダプタからだけ `trusted_external_id:` を受ける。HTTP入力でtrustedフラグを受けない。テストでは合成した外部IDを共通APIへ渡して検証する。
4. **外部明細の版**: 金額（整数）、原取引日／日時、収支、通貨、元明細の状態、取引先・内容等の許可された意味項目を、キー順固定・日付ISO8601・nil/空の区別が明示されたJSONで正規化してSHA-256化する。分類推測・マスタ名照合結果・取込日時・ユーザー修正は含めない。原状態の変更はアプリのクレカ支払状況変更と区別する。欠落と値ありも異なる版。
5. 同一identity+同一payload_digestの最初のEntryを代表とし、後続はreference_entry_idで参照する。Guard下で検索・採番・登録し、参照は必ず代表に直結、循環・多段参照を禁止する。代表が未解決なら参照側も保留として表示し、代表へのリンクだけを出す。代表が確定していれば後続は再登録・再確認せず結果を表示する。別口座・別serviceの同じIDは別identity。

payloadは抽出・アダプタの許可項目だけを保存する。画像bytes/base64、API応答全文、Authorization、URL中のkey、口座番号全文、tokenを保存しない。元画像は現在と同じくリクエスト中だけ利用する。原画像の一時永続保持や期限削除は #70 の設計対象。digest・元口座参照・受付日時・行番号・許可明細・結果・取引snapshotを処理後も保存する。

### 5. 状態・照合・判断

classificationは `new / duplicate / correction / hold`。stateは `pending / held / applied / linked / rejected / superseded / deletion_acknowledged / reference / conflict`。classificationは理由表示用、stateは実行可否。終端（applied/linked/rejected/superseded/deletion_acknowledged）は反映を繰り返さない。referenceの実効状態は代表候補に従う。conflictは新規登録不可で、以前の結果はeventとtarget情報に残す。deletion_acknowledgedは「削除を確認し再登録しない」と利用者が確定した専用終端状態で、単なる未確認のtarget欠落と区別する。

#### 5.1 判定の順序

Guard取得後の最新DB情報で、次の順に判定する。

1. referenceなら代表へ解決する。代表がdeletion_acknowledgedなら**targetの存在・snapshotを検査する前に**確認済み削除の結果を返す。rejected/supersededも確定結果を返す。applied/linkedと、identity経由の未解決候補については既反映先の有無と整合性を確認し、未確認の消失・変更があればconflictを優先する。identityのbound_entryがdeletion_acknowledgedの場合も欠落を新たな矛盾とみなさず、「削除確認済み・新規反映不可」という結果を使う。conflictのものは明示確認なしに終端へ戻さない。
2. 確かな外部IDが同じで同内容の版があれば代表結果を参照する。内容が異なればcorrection+held。金額／日付／原状態等の差分と代表候補・既存取引を表示する。
3. 外部IDがない、または新しいIDでも、既存実績・予定・他の未処理候補と類似照合する。標準検索は **同一の反映口座・同一収支・同額・日付±7日**、月の絞込みなし。取引先／メモの一致は理由に加えるが必須にしない。1件でもあればhold+heldにする。同一文書内の別行も除外しない。画像と将来のCSV、手入力、クイック入力、予定を同じ集合として比較し、入力経路では除外しない。
4. 必須項目が欠ける／Transaction validationに失敗する／元口座とAI推定口座が矛盾するものもhold+heldにする。新規で問題がなければnew+pending。

自動照合の±7日は類似表示の範囲であり同一性の断定ではない。利用者は候補詳細で日付範囲・口座・金額・取引IDを指定し、範囲外や金額違いの既存実績／予定も手動検索して対応付けできる。未処理候補同士を同一と判断するときは、先に登録する代表を明示し、代表の確定後に対応付けする（まだ存在しないTransactionにリンクしない）。

#### 5.2 利用者の操作

- **通常承認**: new+pendingだけを取引作成できる。編集値を受けた場合は保存後に再判定し、類似が出たら登録を停止して確認画面へ返す。
- **同一取引**: 既存actualを選び、候補と取引の差分を確認してlinkする。取引の値は変更しない。金額等が違う対応付けは差分を確認した旨の明示操作が必要。同額・同店というだけの自動linkはしない。
- **既存予定と同一**: plannedを選ぶと、既存idの `entry_type` をactualにする前後プレビューを出す。他項目は維持し、差分を明示して承認後にだけ同じ取引を実績化する。日付や金額を修正したい場合は既存取引の編集画面へ誘導し、戻って再プレビューする。定期予定の自動生成は行わない。
- **別取引**: 確かな同一外部IDによる制約がない場合だけ、比較対象のid・snapshotを表示して「別取引として登録」を選べる。同日同額同店舗の正当な複数件をこの操作で残す。未処理の比較候補も記録する。
- **訂正**: 対応先、元の明細、訂正明細、現行取引の差分を表示し、保留／今回不採用／現行取引との対応を確認する。取引を直す場合は既存編集画面を経てから対応を確認する。訂正候補から新しい実績を追加したり、黙って既存実績を書き換えたりしない。identityが一度も反映先へ結びついていない場合のみ、明示的に「この訂正版を採用」を選び、先行版をsupersededにして1件だけ新規作成できる。先行版が保留のままでも解決できる。
- **保留**: 未解決のまま残す。自動反映も通常の一括承認も実行しない。
- **却下**: rejectedへの遷移と理由を記録し、物理削除しない。同じ文書・同じ外部IDの既知版を再送しても再確認を要求しない。

外部IDのidentityが一度bound_entryを持ったら、新規取引の追加経路へ戻さない。初回linkの相手が手入力であっても同じ。後続版はそのbindingへの確認対象とし、別の取引への無断付替えはしない。訂正を不採用にしても過去のbindingは残る。

#### 5.3 既存取引が変更・削除された場合

保存時snapshotは `date, entry_type, direction, amount, category_id, payment_method_id, account_id, to_account_id, memo, satisfaction, regret, credit_card_status, credit_card_payment_due_on_override, credit_card_paid_on` を含める（idは別保持）。updated_atだけでは判定しない。

通常編集・支払済操作・支払予定日変更・削除で、関連する確定Entryを同じDB transaction内でconflictにし、変更前後を記録する。既存操作は拒否しない。出所詳細と取引一覧に「取込との対応を再確認」を表示する。再送・再承認もsnapshot照合し、callbackを通らない変更があっても、処理時の検出で元の値を戻したり取引を再生成したりしない。

利用者は「現在の取引内容を確認して対応を維持」、削除済みなら「削除を確認して再登録しない」を選べる。前者は新snapshotを記録しlinkedへ、後者は専用終端state=deletion_acknowledgedと確認event（確認日時・歴史ID・削除前snapshot）を同一transactionで保存する。後者でも歴史ID・削除前snapshot・identityのbindingは保持し、欠落の再検査から除外する。変更・削除検知callbackもdeletion_acknowledgedをconflictへ戻さない。再送・再承認・却下再送・一覧／詳細閲覧のいずれも確認済みの結果を返し、再確認も取引再生成もしない。代表に従う参照候補も同じ結果を見る。別の未確認のEntryは従来どおりconflict検査を行い、一つの確認で無関係な対応を解決しない。

### 6. 処理フローと排他

#### 6.1 画像の受付・抽出

1. 画像フォームに取込元選択を追加する。取込元はserviceと元口座を一度設定して再利用し、画面上で確認できる。例示名は契約事実とみなさない。未選択の場合は外部AIを呼ぶ前に説明する。元口座は出所、draft.accountは反映口座として区別し、編集で元sourceを変えない。
2. 現行の形式・8MB上限の検証後にbytesを1回だけ読み、digestを作る。画像ごとにDocumentを作成／取得する。初回受付のmanual_dateとfallback_dateを保存する（再実行で「当日」が変わらない）。画像間で抽出行をconcatしない。
3. 既存Documentがextractedなら保存済み結果へ戻り、AI・Builder・自動反映を繰り返さない。received/failedなら再アップロードされたbytesで再実行する。画面離脱後の処理継続保証は今回追加しない。
4. DB transactionとGuardの外でGeminiを呼ぶ。並行再送で同じAI呼出しが重なる可能性は残るが、保存結果は1つに限定する。費用／再試行制御・Job・受付後永続bytesは #70。
5. 成功時にGuard→Documentの順でロックし、再読込する。すでにextractedならこの応答を捨てて既存結果を返す。未完了なら同じtransactionで全Entry・draft・eventを作りextractedにする。0行成功もextractedとして記録する。全行作成後に類似判定し、同じ文書内の候補も照合できるようにする。
6. 失敗時もGuard下でextractedでない場合だけfailed+安全なエラーコードを記録する。後発の失敗が先行成功を上書きしない。失敗後の再送では成功済み文書を解析しない。
7. 設定が承認不要の場合は新規作成した未処理Entryだけを共通Applierへ渡す。ファイル成功commit後・反映前に切断した場合、再送だけで新規反映を再開せず、保存済み候補を画面で承認できる（過去候補への設定変更の遡及適用を防ぐ）。

複数画像では初回の新規Documentとdraftへ既存と同じrequest内batch_idを渡す。既存Documentのbatch_idは再送で変更しない。create後は `image_import_drafts_path(document_ids: [...])` で今回対象の正規Document集合を表示する。既存batch_idリンクも維持する。部分失敗・空検出・解析未完了も画像単位で表示し、「候補なし」を成功と未処理の共通表示にしない。

#### 6.2 共通の反映・判断

候補1件を1transactionとして、Guard→Document→Entry（参照なら代表もid順）→Identity→比較対象Transaction/Entryをid順、で排他する。DB情報はロック取得後に読み直す。MySQLの古いsnapshotに依存しないよう、照合・整合確認に使う既存行はlocking readを用いる。外部呼出しやビュー描画はtransaction外。

newの反映は、最新値の再分類 → `Transaction.create!` → target id/snapshot → Identityの初回binding → state=applied → eventを**同じ接続の同じtransaction**でcommitする。link、予定の実績化、訂正版の初回採用、却下も同じServiceから同様に処理する。

`bulk_approve` はIDを重複排除し、1件ずつ処理する。途中の1件失敗はその候補の書込みだけrollbackし、成功件数／失敗・保留件数を表示する。処理済み候補への承認・却下競合は、先にcommitした終端結果を返し、状態を上書きしない。削除HTTPも内部ではrejectに置換する。

明示的な同一／別／訂正版採用／矛盾確認では、署名付きreview_tokenに候補id・lock_version・編集値digest・比較集合のidとsnapshot digest・選択する操作／対象・期限（30分）を含める。プレビュー生成後の編集・追加候補・対象削除・期限切れなら再プレビューを要求し反映しない。単なるnewの一括承認は、再判定で新たな類似が出れば停止する。

`RecordInvalid`はrollback後に別transactionでGuardを取り直し、エラーコードと編集途中値（許可カラムだけ）を保存して修正可能にする。再読込で他の操作がすでに確定済みなら編集値で上書きせず、その確定結果を返す。書込み失敗時はtransactionオブジェクトを使い回さず再読込する。DB一意制約違反・deadlock・lock timeoutの救済はtransaction外で行い、最大2回、Guard取得から再実行する。それでも失敗なら安全な失敗表示で終了し、候補は未反映のまま再実行できる。接続断でcommitの成否が不明なら同じキーで再読込し、targetがあれば結果を返す。未commitなら再実行可能。失敗eventを書けなくても成功を返さない。

#### 6.3 通常の取引書込みとの整合

`ImportGuard.synchronize` は必ずDB transaction内で `ImportGuard.create_or_find_by!(name: "ledger")` によりsingleton行を確保し、返された永続行へ `lock!` してからblockを実行する。nameの一意性はDB unique制約を使い、競合insertを妨げるモデルのuniqueness validationは追加しない。Rails 7.1.6のcreate_or_find_by!はrequires_newのsavepointでunique違反を処理して既存行を取得するため、PostgreSQLの失敗済みtransaction内で独自に例外を握り潰さない。初回の通常取引保存・schemaから再構築したDBでも同じ経路で初期化でき、seedの手動実行やmigration内データ投入を前提にしない。Guardを削除するアプリ操作は提供しない。作成失敗／ロック取得失敗ならblockを呼ばず書込みを止める。ロックは外側の取引transactionのcommit/rollbackまで保持し、callbackからの呼出しも同じ方式・接続を使用する。

`Transaction` に新しいconcernを追加し、`before_save / before_destroy` で同じGuardを取得、`after_update / after_destroy` でtarget整合性を更新する。callbackを通る既存rakeや通常のmodel操作も対象。callbackで `Transaction#lock!` して編集中の属性を消さない。全Serviceは最初にGuardを取得する。

`TransactionsController` のcreate/update/destroy/mark_credit_card_paid/shift_credit_card_payment_due_onも、対象の取得・再取得と書込みをGuard内へ移す。支払済の複数件はid順。予定→実績化のApplierもGuardを取得してから変更する。callbackが記録したconflictのうち、明示操作で確認した当該Entryだけを同一transaction内で解決できる。他の対応は勝手に解決しない。

単一利用者・小規模のため短いDB書込みを1行Guardで直列化する。別sourceの類似画像の同時自動承認も後発が先行Transactionを認識し保留になる。ロックを迂回するbulk SQLでの取引更新は共通APIの対象外で、既存コードにその経路はない。外部から直接DBを変更した場合も再処理時snapshot照合は働く。

### 8. DB移行と既存データ

DDLはRails migrationの両adapter共通機能（JSON、通常unique index、FK）だけを使う。部分unique index、DB固有enum、JSON検索での同一性判定、MySQL固有collation指定を使わない。digestは64桁の小文字hexをvalidationし、元IDはdigest衝突チェックでバイト列比較する。異なる元IDでdigestが一致した場合は保留／エラーとし同一扱いしない。

1. 新テーブルとnullableなdraft.import_entry_idを追加。
2. migration内部の匿名ARクラスで、固定 `legacy_image` Source（account=nil、元口座不明）を作成。現存draftをbatch_idごとにlegacy Documentへまとめる。content_digestは画像hashと誤認しないよう `SHA256("legacy_batch:" + batch_id)`、channel=legacyとする。
3. 既存draftのid順にEntry（payloadは現在の値、元画像・真の抽出値は不明と明記）と移行eventを作成して紐付ける。state=held、reason=legacy_origin_unknown。旧候補は自動適用せず利用者が確認できる。batch_idとdraft.idは維持。
4. 全draftの参照を検証しNOT NULL+uniqueを付ける。件数が多ければ分割batchを使い、再実行で二重backfillしない（draft idに基づく識別を利用）。MySQL DDLの暗黙commitを考慮して途中再実行可能にする。
5. すでに承認／却下され削除済みのdraftとTransactionの対応は復元しない。既存Transactionは書換えず類似照合・明示linkの対象にする。過去画像のhashも復元不能なので、初回再アップロードは新Documentとなり、既存取引との類似確認を経る。

適用時は画像受付・承認を停止してからmigrationとコードを切替え、NULL候補が生成される旧コードとの並行稼働を避ける。DBへの適用・本番運用切替は実装と区別し、今回は実行しない。移行済み出所を失うdownは自動提供せずirreversibleとする。

### 9. UI・件数・表示

文書詳細と今回のDocument集合のサマリで、新規・重複・訂正・保留の件数と行ごとの理由を表示する。classificationは重複しない1区分を採用し、保留の内訳（未確定／矛盾／未完了）を示す。correctionの未処理は訂正件数に数え、保留にも二重加算しない。参照側は代表未処理なら保留、代表確定済みなら重複として分類する。

### 11. 回帰リスク・運用上の限界

- 最も大きい変更は候補を消さず状態を残すこと。既存requestの「処理後draftが消える」という期待はpending scopeへ変更し、未解決・処理済み一覧とサマリを区別する。batchの既存URLを維持する。
- 原画像が異なりIDもなく、標準照合条件にも一致しない同じ取引を完全自動同定することは約束しない。手動検索・対応付けを用意する。同日同額同店舗は削除・統合の根拠にしない。
- 出所と結果は増加する。通常一覧は50件ずつ、比較はsource/account/date/amountのindexで限定し、detailsの巨大payloadを一覧でpreloadしない。`transactions` に `(account_id, direction, amount, date)`、draft側にも同じ比較用indexを追加する。
- 一行Guardは書込みを直列化するが、単一利用者の短いtransactionに限定する。全てのGemini通信はロック外。分類・手入力・残高集計の計算式自体は変更しない。
- legacyで失われた出所を捏造しない。移行前の同一画像再送の識別はできないため、既存取引との類似確認が必要。

技術参照: Rails 7.1.6の [悲観的ロック](https://api.rubyonrails.org/v7.1.6/classes/ActiveRecord/Locking/Pessimistic.html)、[transaction・rollback](https://api.rubyonrails.org/v7.1.6/classes/ActiveRecord/Transactions/ClassMethods.html)、[create_or_find_by!](https://api.rubyonrails.org/v7.1.6/classes/ActiveRecord/Relation.html#method-i-create_or_find_by-21)。unique違反のsavepoint内処理はRailsのAPIを使用し、外側へ伝播したDB例外後の再実行はtransactionの外側から行う。
